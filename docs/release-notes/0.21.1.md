AudioPlaybackKit 0.21.1 resumes a route change or renderer stall from the audio it already wrote,
instead of seeking the item source.

No public API changes. Decode is unchanged.

## What changed

- **An auto-flush or stall no longer seeks the source.** When the renderer drops its queue (a route
  change such as CarPlay or AirPlay, a new output configuration, or a stall), the feeder enqueues the
  audio it had written from the frame the renderer stopped at, and the source decodes on from where it
  was. A transcoding server is no longer reopened at a rounded offset, so the song does not jump and
  there is no silence while the stream reopens (Shuttle Music #1120). The feeder keeps a copy of what
  it has written ahead of the playhead, up to 30 s, about 11 MB at 48 kHz stereo. A burst of flushes,
  as route changes send, replays on from the same copy, including what a shallow route had not yet taken.
- The source is still seeked, to the exact frame, when that audio is gone: a flush time behind the
  playhead's chunk, or a flush while a processor or speed change is re-feeding. A processor or speed
  change while a replay is still being written drops the rest of it and seeks the source from there,
  so the change applies as before. A renderer failure
  or media-services reset rebuilds the output and still seeks, as before.
- Processors are not flushed by an auto-flush any more: the replayed audio is what they already
  produced, so their state carries on as if nothing happened. An app source wrapping
  `FFmpegItemSource` sees no `seek(toFrame:)` for a route change.

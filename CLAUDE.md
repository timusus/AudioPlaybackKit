# CLAUDE.md

Public (MIT) Swift package, **AudioPlaybackKit** (`timusus/AudioPlaybackKit`), holding the iOS decode
layer used by **Shuttle Podcasts** (`timusus/shuttle-podcasts`) and **Shuttle2** (`timusus/shuttle2`). It holds only decode,
byte-source and FFmpeg code; effects (skip-silence, Voice Boost) and anything about podcasts, ads,
queues, players or UI stay in the apps. Docs are in `docs/`; start at `README.md`.

## Layout

| Product | Target(s) | What it is |
|---|---|---|
| `PlaybackDecode` | `PlaybackDecode`, `CStreamDecode` | `FFmpegStreamDecoder`: pull decoder over a `StreamByteReader`, Float32 interleaved, seekable, cancellable. `FileByteReader` is the plain-file reader. Probe budget is `StreamProbeBudget` (default 64 KiB / 1 s). |
| `PlaybackStreaming` | `PlaybackStreaming` | Opt-in network byte source: `GrowingFileByteSource` over an HTTP(S) URL writing a growing file, with retry/resume. Rules live in the internal state machine `GrowingFileDownload`. Depends on `PlaybackDecode`. Auth headers arrive resolved; no feed or podcast concept. |
| `PlaybackStreamingTestSupport` | same | `LoopbackMediaServer`, no fixtures. |
| `FFmpeg` | `CFFmpeg` (headers, module), `FFmpeg` (binary) | The dynamic FFmpeg framework, for an app with its own C against libavformat. An app links exactly one FFmpeg. |

`Frameworks/FFmpeg.xcframework` (ios-arm64, ios-arm64-simulator, macos-arm64) is **committed to git**
(about 5 MB): SwiftPM does not run Git LFS and there is no CI to publish release assets. The framework
binaries are binary in `.gitattributes`. `VERSION.txt` inside it records the tag, configure flags,
patches and linkage. The headers sit in `Sources/CFFmpeg/include`, also generated by the script.

## FFmpeg

- LGPL-2.1 only, shipped as a dynamic framework each closed-source app embeds so users can relink
  (ADR-0001); never link it statically or enable mergeable libraries. Never add `--enable-gpl`,
  `--enable-version3`, `--enable-nonfree` or an external library beyond the system zlib.
- One music-superset build for both apps (ADR-0006); the lists are at the top of
  `scripts/build-ffmpeg.sh`. Each format needs a conformance fixture.
- `scripts/build-ffmpeg.sh` takes several minutes; run it in the foreground and commit the framework
  alone as `build: rebuild ffmpeg ...`. Patches live in `scripts/ffmpeg-patches/`.

## Commands

```sh
swift test --filter <Class>                         # iterate on the tests you touch
scripts/test-fast                                   # before you finish: all but conformance, parallel, about 90 s
scripts/test-all                                    # whole suite, about 490 s: land and releases only; a bare `swift test` is serial, slower still
swift test --filter PlaybackDecodeConformance       # about 410-480 s (the matrix test alone about 234 s)
GOLDEN_UPDATE=1 swift test --filter PlaybackDecodeConformance   # after an intended change; review the JSON diff
xcodebuild test -scheme AudioPlaybackKit-Package -only-testing:PlaybackStreamingTests \
  -destination "$(sim destination)" -parallel-testing-enabled NO -collect-test-diagnostics never   # an exclusively held pool simulator
```

Iterate with `--filter` and finish with one `scripts/test-fast` run (`--filter` and other args pass
through; `--with-conformance` adds the conformance bundle). Conformance runs only when decode or demux code
changes. `land` skips conformance unless the batch touches `Sources/{PlaybackDecode,CStreamDecode,CFFmpeg}`,
`Frameworks/`, `Package.swift` or the conformance tests (`scripts/test-fast --print-needs-conformance <base>`).
CI runs the full gate on every PR.
`scripts/test-fast` writes `.build/test-fast.log` and prints a verdict: read the log, and never pipe test
output through `tail` or `head`, which hide the verdict (swift-testing's "Test run with 0 tests" is not the XCTest result).

On a build with the FFmpeg xcframework only the two generated-MP3 tests (30-minute CBR, 5-minute Xing VBR) skip, without host `ffmpeg` and on iOS;
the `XCTSkipUnless(FFmpegStreamDecoder.isAvailable)` guards skip only without it. Known decoder
bugs run under `XCTExpectFailure` (`KnownIssues.swift`, e.g. #55). Conformance details, known
issues and fixtures: `docs/contributing.md`. Consumers pin a tag, never a branch. A public API change
is a minor bump at 0.x; so is any decoder change that alters PCM, and the release note says what moved.

## Formatting

`.swiftformat` is the style (`brew install swiftformat`). Install the pre-commit lint once per clone with
`git config core.hooksPath scripts/git`; it runs `swiftformat --lint` on staged Swift files and names the fix
(`swiftformat <files>`). `.claude/format-on-edit.conf` formats each file Claude edits. `land-verify` lints the
whole tree first. `.git-blame-ignore-revs` hides the baseline reformat (`git config blame.ignoreRevsFile .git-blame-ignore-revs`).

## Conventions

- Testable first: anything touching time, the network, the file system or the OS sits behind a seam a
  test can drive. A behaviour without a deterministic test is not done.
- One mechanism per concern (one recovery layer, one seek path); no speculative options. Fix the root
  cause, never paper over a symptom.
- When in doubt follow androidx/media (media3): its `DataSource`, `Extractor` and
  `DefaultHttpDataSource` code and issues are the reference for edge cases. Cite the class or issue
  in the ADR or commit, and say why when deviating.
- Conventional commits (`feat:`, `fix:`, `refactor:`, `build:`, `docs:`, `test:`). Work on a branch and
  open a PR; CI (`.github/workflows/ci.yml`) gates it. No AI attribution in commits or PRs.
- Public API is the contract with two apps: `public` only when an app needs it, `Sendable`-friendly.

## Code health (codehealth)

- Before editing a file, run `codehealth here <files>`. It prints what those files already carry: open findings
  by finding unit, the Start here entries naming the file, and its cycle, hidden-coupling group and layer.
  Under 2 s once `build/codehealth/report.json` matches HEAD; the first run after a new commit rebuilds it.
- A repo with `brief=on` in `.claude/codehealth.conf` may print up to five fact lines (`codehealth brief <file>`)
  before your first edit of a file: what reaches it, what it changes with, its tests and times, open findings.
  It prints nothing while the report is rebuilding.
- The same opt-in runs `codehealth edit-check <file>` after each edit of a production file: up to eight
  `path:line:` facts (syntax errors, new imports nothing declares, changed public signatures and the lines that
  call them). It is a parser and an index, not a compiler: nothing printed means it found nothing.
- Before planning work across several files, read **Start here** in `build/codehealth/report.md`.
- Before you commit or land, run `codehealth gate --base origin/main`. Exit 0: nothing new at warning or above.
  Exit 1: your change added a blocking finding. Exit 2: the tool failed, not your change.
- A block states a fact about the diff and the principle it breaks. Whether and how to fix it is your call; a
  `hint` is an optional suggestion. Rerun the gate after a change.
  If the finding is wrong for this site, suppress it with a stated reason:
  `// codehealth-ignore <rule>: <why this site is accepted>` on the line or the one above.
  A bare ignore prints a warning and is itself a finding. Rule-wide choices go in `.claude/codehealth.conf`
  (`disable=<rule>`), old debt in `codehealth baseline`.
- Never work around the gate: no splitting a change to dodge a rule, no editing code just to silence one.
- `build/codehealth/` is generated; don't commit it.
